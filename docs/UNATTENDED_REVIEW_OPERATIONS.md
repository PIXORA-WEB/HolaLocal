## Confirmed implementation

Account erasure: accountDeletionFinalizer.js records leases, request versions, checkpoints and failed_retryable state. It checks ownership before and after lease acquisition and stops on integrity/ownership blockers. Failure may return an operational response rather than throw an ERROR; generic error/HTTP5xx alerts miss such failures. AdminAccountDeletionsPage invokes retry manually. Only retention/media sweep schedules exist in index.js; no automatic account-erasure resumer found. Retryability does not mean automatic retry. This is an existing platform gap, not evidence that a real account erasure is currently stuck.

Retention: existing hourly authenticated worker, one instance, max50 candidates per collection per run. Three collections (reports/requests/audits), transactionally rereads expiry, never deletes an open report based only on expiry. A partial run is idempotently resumable on the next schedule. However, a persistent exception aborts the current invocation and can repeatedly block the same leading candidate or collection; maxInstances1 is not a complete deduplication/lease guarantee. Missing or malformed expiry fields can escape the query entirely. Disabled worker performs no cleanup. Monitoring metadata/preflight must not claim that successful Scheduler delivery proves correct deletion.

## Recommended safeguards before unattended launch

1. Erasure: periodic read-only health detection for requested backlog, failed_retryable, expired finalizer leases and lack of progress. Emit only counts/age buckets/fixed failure classes; no account identities in notifications. Durable incident state should notify once per continuing condition with significant-change escalation, not repeat every poll. Initial requested erasure remains the existing authorised admin workflow, including owned-business/privileged-account blockers.
2. Bounded automatic resumption only for a workflow already authorised/started by an admin, with recorded approval/version, an expired/no-active lease and retryable transient failure. Reuse the authoritative finalizer primitives and ownership/integrity checks; do not forge an admin identity, auto-finalize merely requested/cancelled work, or skip a failed checkpoint. Exponential backoff, attempt/run caps, durable progress, idempotency, authenticated worker and a terminal/manual-action state are required. After retry exhaustion retain evidence and a visible unresolved condition; never mark deletion complete or silently discard identifying data. This requires a separate reviewed implementation/deployment and tests, not an IAM or status workaround. A calendar reminder alone is not an adequate automatic safeguard with no guaranteed human response.
3. Retention: isolate per-record/collection transient failures so unaffected eligible records can progress, using bounded work and durable failure/quarantine metadata that contains no copied private text. Do not broaden expiry/state criteria or delete open reports to drain a queue. A permanently bad first page must not starve later eligible records; choose/test a cursor or equivalent safe progress mechanism. Detect malformed/missing expected expiry on resolved records without auto-inventing expiry. Monitor oldest due age, repeated page saturation, failure counts and completion heartbeat. Automatic retry for transient failure is appropriate; automatic status changes, shortened retention or sweeping invalid records are not.
4. Failure of the safety checks should inhibit RETENTION activation and new risky automation, not automatically disable business registration/approval. After activation, pause cleanup on systemic invariant violations; keep ordinary reviews usable with original-text fallback where safe. Do not automatically disable account-erasure cleanup on a translation failure. Translation requires separately approved cost controls; alerts cannot substitute for spend limits.

These safeguards are recommended launch blockers for a reliably unattended reviews/retention rollout unless an explicit alternative operating arrangement is agreed. Current safe-stop protections prevent many destructive mistakes, but they do not guarantee eventual erasure/cleanup without a responder. No new automatic worker or deletion behaviour is implemented in this preparation; approve the concrete scoped safeguard work before a deployment package expands beyond current review exports.

## Notification restraint and verification

Prepared log policies have24-hour rate limits/no repeat interval. Overlapping callable5xx/latency policies are diagnostic-only (no email channels); retention worker errors route via Scheduler failure rather than duplicate generic runtime error email. This reduces duplicates, not global exactly-once delivery. Distinct incidents may still need separate actionable messages; an hour/day cooldown must not hide an unresolved critical state forever. Scheduled completion absence and state backlog cover different failures and should eventually share durable incident keys where feasible. No staffing/SLA wording belongs in public UI or notifications.
